# 章节职责与优化准则

本文件整理科研论文各核心章节的职责边界与去 AI 味组织准则。固定的句数、词数、段落数均不是硬性验收条件，应服务于清晰传达技术事实与论证链。

## 1. 引言第一段：建立任务对象，而非连续宣告重要性

需要回答：研究对象是什么，实际观测或输入条件是什么，待求解或待恢复的目标是什么。

可保留一到两句应用或物理背景，但每句都应提供新信息。连续出现“应用广泛、需求增长、技术进步、潜力巨大、迫切需要”时，检查是否只有空泛评价而没有实质解释。

“应用场景多”不会仅凭连接词就自动推出“某类硬件需求激增”；“采样次数增加”也不自动等价于“有效信息充足”。现有材料仅说明观测机制时，直接陈述观测与求解任务，不凭空补造产业规模、实时性或成本优势等未经核实的结论。

## 2. 已有进展：客观归纳已有能力，铺垫问题边界

先按信息利用方式或建模假设归纳相关工作，再选代表性方法具体说明。取舍标准是能否支撑后续问题提出，而非按年份罗列文献流水账。

引用前人工作时，区分其原始实验设置（如单帧观测、理想标定、同分布测试）与本文设置之间的边界，不把其他任务中的特定结论直接移植到本文场景。

## 3. 从进展到挑战：建立实质桥梁，不杜撰统一缺陷

按以下三步核查段落过渡，不要求机械套用固定句式：

- 上一段已确立哪类建模能力或常见做法？
- 本文所处设置引入了什么具体物理、统计或计算属性？
- 在该属性下，哪一个具体环节仍未被上述做法妥善处理？

通用结构参考：`[有文献支撑的做法或能力]. Under [本文具体条件], [可验证的系统属性] leaves [具体未解问题].`

若讨论仅针对某一方法子类，直接在主语或条件中限定（例如 `In split-variable formulations with scalar penalty weights, ...`），避免使用 `Unlike all existing methods...` 这类既易失真又显浮夸的全称否定。

不得为了行文顺畅，将“本文选择某种优化框架”写成“问题病态性必然唯一要求该框架”；也不得把“需要正则化”直接等同于“必须采用本文特定模块”。

## 4. 挑战段：标签、原因、后果各司其职

若作者采用两到三个加粗短标题概括核心挑战，属于清晰的导读组织方式，不应按通用散文规则一刀切删去加粗。

标题应平行且直指问题；正文先给出具体结构或物理限制，再写出读者可理解的直接后果。避免：

- 用 `must coordinate / needs integration` 等方案要求代替缺陷分析；
- 用 `ill-posed`、`challenging`、`complex` 等笼统标签代替机制解释；
- 把“权重无法按分量调节”换词重复成“难以适应分量间差异”；
- 在后果从句中塞入缺乏实验支撑的严重伪影或全面失效断言；
- 只甩出 `as shown in Fig. 1` 却不在正文解释图意。

## 5. 方法提出段：先讲核心改变，再引出实现组件

以针对挑战的核心机制变化为主线，交代输入、运算动作和输出。引入经典算法框架（如展开优化、变分推断、状态空间模型）时，用一句话点明它在本文中组织变量更新的具体角色，而非只贴算法标签。

引言中的方法概述聚焦核心自由度、约束形式与求解性质，不必塞入网络层宽、数值下界常数或完整矩阵求逆展开式。辅助特征提取或跨阶段传递模块各用一句说明输入输出作用即可，不要因为起了模块缩写就将其拔高为与核心理论并列的主贡献。

## 6. 贡献列表：保留有意平行，区分贡献层级

常见的三段式贡献（核心方法/机制 + 关键支撑组件 + 系统实验验证）以及平行的 `We propose / We introduce / We demonstrate` 句首，在科研论文中属于高可读性的规范约定：

- 每条贡献对应可定位的设计或实证发现，而非单纯的模块命名清单；
- 禁止从参考范文中照搬 `for the first time`、`state-of-the-art` 或超出本文测试范围的普适声称；
- 声称两个模块“互补协同（complementary）”时，必须有对应的消融对照支撑；
- 用户明确采用三条贡献时不因规避所谓“三元排比”而强行拆并。

## 7. 摘要：独立成篇，核心机制占主导

推荐依次涵盖：任务背景、具体瓶颈、核心思路、必要支撑设计、主要实验结论。

抽象名词过密时，优先把核心机制改写为“主语 + 具体动词 + 作用对象”，而非再造一个新概念包装盒。模型全称首次给出后用缩写或明确代词衔接。注意区分设计属性与实证结论：`compact parameter count` 需有参数/计算量支撑，`strong cross-domain generalization` 必须对应未见域测试实验，不能仅从条件化结构本身推导出来。

## 8. 方法与图注：先交代功能角色，再给精确定义

方法节中每个符号应有稳定定义与维度说明；架构图中保留追踪数据流所需的最小标签集。图注负责说明图中模块、箭头、线型以及示意图与实测曲线的区别，不整段粘贴正文公式推导。

严格区分物理观测项、学习先验、罚参数、置信权重与最终输出估计。正定性、闭式解条件、跨阶段共享或独立参数等属于硬性数学事实，绝不能为了“降低专业词密度”而删改失真。

## 9. 实验：客观事实与机制解释分层陈述

先交代验证问题、数据集与协议、评价指标和定量观察，再讨论结果支持什么推论。不把规划中的实验写成已完成结论；不把“采用相同数据集”默写成“训练轮数、损失函数与权重全部一致”。

消融实验应逐一指明被隔离的变量；诊断实验（diagnostics）如实称为诊断分析，除非实验设计确实完成了因果隔离，否则不轻率升级为 `proves the underlying mechanism`。

## 10. 结论：回扣核心设计与验证边界

结论通常只需简明收束：提出了什么核心设计、主要实验证据表明了什么、该设计在对应任务条件下带来了什么实质能力。

默认不在结论引入新术语、新因果猜想或未测场景外推，也不逐句复读摘要。若作者已锁定特定收束句式，在润色时尊重其句式基准；若其中个别定语超出当前实验覆盖面，单独列出证据核对提示，不静默篡改作者原意。
