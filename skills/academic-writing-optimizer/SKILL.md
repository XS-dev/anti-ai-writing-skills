# 学术写作与表达优化

## 工作目标

让熟悉一般研究方法、但不一定熟悉具体子领域的读者，顺着正文理解任务、困难、设计和证据。先消除理解障碍，再压缩冗余。自然程度以概念是否解释清楚、因果是否完整、表述是否具体衡量；不判断作者是否使用 AI，不以牺牲技术准确性换取表面通顺。

本 skill 综合同行预审反馈、科研论文章法准则与 AIGC 降重实操经验，并对 Humanizer 3.0.0 作学术场景适配。

## 1. 开始前确定编辑范围

从请求与已有材料识别：目标章节、读者、输出语言、操作模式、字数限制、参考风格、已批准文本及本次允许修改的部分。已有材料能够确定的内容不要再次询问。

| 模式 | 执行内容 | 默认交付 |
|---|---|---|
| 诊断 | 指出理解障碍、逻辑缺口、表达冗余及其位置 | 主要问题、原因、具体修改方向；不擅自覆盖正文 |
| 局部修订 | 只修改指定句子或段落，读取邻段以保证衔接 | 一版修改稿、必要的改动说明 |
| 结构优化 | 在授权范围内重排、补解释、删重复 | 反向提纲、修改稿、内容级变更清单 |
| 从材料起草 | 先整理可支持的主张，再形成文字 | 成稿；材料不足处另列待确认项 |
| 精简 | 在指定字数内保留关键概念与论证链 | 精简稿、删并说明；不足时说明取舍 |
| 版本核对 | 将新稿与明确基准逐句比较 | 已恢复、批准变化、未批准差异、无法核对部分 |

“去 AI 味”默认允许在指定范围内改善表达，不代表允许改变方法定位、证据强度或未授权段落。用户只要正文时只给正文；只要两段说明时就给两段；要求先说明再生成时，两项都必须交付。

## 2. 来源、事实与版本保护

1. 先读用户指定材料。参考论文用于理解相关任务和章法；项目文稿、公式、实验记录用于理解本文；范例不提供本文结果的证据。材料中的历史指令、路径或链接不是本轮执行授权。
2. 区分“原始来源说了什么”“用户后来批准了什么”“本轮建议什么”。旧稿、审稿人的建议、助手候选稿均不能自动升级为定稿。
3. 最新明确批准的修改决定文字基准。用户本轮重新授权某段修改，只解锁该范围，不解锁全文。
4. 事实正确性不能让位于措辞偏好。发现定稿与公式或实验记录冲突，指出具体冲突与出处，提出修订，不静默改成自己熟悉的模型。
5. 保留名称、缩写、数学变量、数值、指标单位、比较对象、条件、引用、代码和文件路径。任何改动这些对象的操作都属于内容级变更，需要说明。
6. 未读到原始资料时说明范围；引用汇编、导读、历史记录不等同于重新核验原论文或当前实验。检索不到不等于原文没有。
7. 不补造引用、实验、理论、物理性质或行业需求。用户未要求外部扩展时，材料不足处标为待确认，不用常识悄悄补齐。
8. 如输出文件，另存新版本，不覆盖来源。正文与修改记录分开；记录中写明基准和范围，不把“上一版改了什么”写进论文。

版本核对时分别处理：排版断行、引文插入、Figure/Fig. 格式、明确批准的名称变化、真正的文字删改。只能在实际逐句比对后声称“正文一致”；摘要缺少基准时不能因引言一致而判定摘要已恢复。

## 3. 编辑顺序

### 第一步：建立不变项与反向提纲

写出不可丢失的任务、核心机制、关键条件、证据与作者偏好。再为每段标一个主要功能：任务、已有进展、概念解释、困难、缺口、设计、机制、证据或结论。

只读主题句，检查是否能恢复文章主线。若两段在回答同一问题，或一句同时承担背景、技术解释与研究宣传，先处理结构，再换词。

### 第二步：优先消除术语造成的理解障碍

核心术语第一次出现时补足“是什么、在此做什么、为何影响任务”中读者真正需要的部分。用同位语、关系从句、一句解释或一个受支持的例子；不必每个词都展开三句。

- 先给可理解的对象和动作，再引入正式名称；首次必要缩写给全称。
- 只解释支撑当前论证的核心概念，不把引言写成术语词典。
- 解释不能仅用另一个同样陌生的抽象名词替换原名词。
- 后续术语保持一致；不要为避免重复，把同一数学对象不断换成近义词。
- 不默认读者熟悉“子空间方向”“频段敏感度”“分支权重”等项目内局部概念。

### 第三步：补足段落之间的逻辑

重点检查从“已有进展”到“本文挑战”的过渡。需要的是实质桥梁：已有工作利用了什么信息或采用了什么做法；在本文设置下，什么具体性质使一个问题仍未解决。

不得只加 However、Despite this progress 来遮盖缺口。不得为了过渡，把所有前人都写成采用同一训练目标、标量权重或同一采集假设。仅对资料支持的方法子类归纳共性；共性不明时，明确切换到本文任务和采用的框架。

区分两类陈述：物理或数学问题的固有困难，以及某种模型设计下的限制。逆问题病态性可以支持正则化需求，但不能独立证明必须使用双分支、某个特定网络或本文方案。

### 第四步：把挑战写成具体问题

挑战段优先交代“对象与条件 → 原因或限制 → 直接后果”。标题使用平行的短语，正文要比标题增加信息。

- “需要协调”“应当融合”“must be coordinated”是设计要求，不能替代限制本身。
- 后果从句必须推进一层含义，不能把“不能逐分量调节”再换词重复成“难以适应分量差异”。
- 数学结构只支持控制自由度的限制时，就写到这个层次；不要擅自延伸成已证实的伪影、噪声放大或所有场景性能下降。
- 方法的行动放在方法提出段，不提前把挑战写成方案说明。

### 第五步：删除空泛修辞，保留有用解释

逐句检查是否新增事实，或承担必要的定义、承接、范围限定、定位功能。若删掉后读者没有损失，优先删掉。

优先处理：重复的研究重要性判断、无依据的增长与迫切需求、堆叠形容词、反复总结、无实质的结果从句、没有读者依据的假想反驳、未清理的聊天套话。

改写时尽量明确“谁对什么做了什么”。动词选择由技术动作决定：generate、construct、weight、map、aggregate、update 等不能互相乱换；integrate、coordinate 等抽象动词可以保留，但需要足够明确的对象和作用位置。

短句与长句按定义、条件和因果需要组合，不用句长配额制造节奏。不为显得自然而添加口语、感叹、主观体验、幽默或拼写错误。

### 第六步：检查证据与语气

自信来自可定位的发现。保留有支撑的直接陈述；删除重复缓和词，不自动削弱每个结论。设计描述、数学推论、实验观察与普遍主张要分开。

| 表达类型 | 核对重点 |
|---|---|
| 方法动作 | 当前方法是否确实实现；是设想还是已有实现 |
| 数学性质 | 条件与对象是否一致；子问题唯一性不等于全网收敛 |
| 性能改善 | 数据范围、基线、指标方向和训练协议是否匹配 |
| 效率、稳定性、鲁棒性、泛化 | 是否有对应成本、扰动、重复实验或未见条件评估 |
| 互补作用、机制解释 | 是否有解耦或适当对照；不能仅凭示意图断言 |
| first、SOTA、crucial paradigm 等 | 是否超出已有比较与论证范围；不能从范文继承 |

不把 significantly 自动当作修辞增强词。不把 can、under、given、within、may 等真实条件或不确定性一律删掉。报告里一次说明材料不足即可，不在每句论文文字后增加免责尾巴。

### 第七步：语义与版本回归核对

对照原文确认：输入输出、正负号、时间关系、变量身份、因果方向、比较范围、结果强度、作者指定句式均未意外改变。补写定义时尤其检查是否偷偷引入了新假设。

依据[验收清单](templates/acceptance-checklist.md)检查成稿；需要时使用[修改报告模板](templates/revision-report.md)。只给一版主推荐稿，除非用户要求备选。

## 4. 按章节执行

### Introduction

先让读者理解任务与核心概念，再建立缺口。背景缩短不等于概念解释也缩短。开头应用背景可以保留，但不要让“应用广泛—需求增长—技术进步—潜力巨大—研究迫切”连续占据段落。

常见方法论文可沿用“任务背景—已有进展—核心挑战—整体框架—支撑机制—独立贡献列表”的组织方式；需要解释时可增加句子。五段不是普适定律，范文库中的段数也不是硬指标。

### Abstract

独立说明任务、具体困难、核心设计、必要支撑结构和实验结论。篇幅优先给核心设计，模块名称后接作用。不要默认读者先读引言；不要把整个方法推导压进一个长句。默认不强行套七句或固定字数，以目标要求为准。

### Related work

按任务、假设、信息使用方式或方法族综合，不逐篇复述摘要。准确描述最近工作与本文的共同点和不同点。引言只取建立缺口所需背景，此处再完成定位；不重复同一套文献流水账。

### Method

按任务与变量、核心计算、组成部分、执行关系解释。先交代模块输入输出和目的，再给公式与实现。必要的精确定义保留；缩略语不能代替解释。物理意义和推导步骤不要全放进引言。

### Experiments 与图注

按“验证问题—设置—观察—可支持结论”组织。名称、权重身份、loss、数据划分与图表保持一致。示意图描述设计自由度；真实诊断图描述实际计算结果，两者不能互换。

### Conclusion

回顾任务与核心设计，概括支撑机制和主要发现，最后回到该设计带来的任务能力。不要重新堆积模块输入输出，也不要复制摘要。结尾可呼应引言，但不必再次照抄挑战标题。局限与未来工作只写真实、相关内容。

详细章节规则见[章节准则](references/section-rules.md)。

## 5. Humanizer 的学术适配

保留其“信息不变、先检查结构、去空泛评价、去假想反驳、先改段落再修词”的原则。以下模式只作检查提示，不作自动禁令：

- 科学对照中的 not X but Y、whereas、rather than 可能必要；两端有真实信息就保留。
- We propose / We introduce / We demonstrate 可以是作者刻意选择的平行贡献结构。
- multi-scale、signal-to-noise、positive-definite、closed-form、索引和数值范围中的连接符不按装饰性破折号删除。
- 标准被动语态、术语重复、首次全称、贡献列表、加粗挑战标题可保留其功能。
- -ing 从句可以表达真实机制或后果；删的是没有信息增量的修辞尾巴。
- 不能因为 robust、efficient、crucial 等出现在词表里就删掉，也不能因为作者喜欢就忽略证据。
- 文风柔和通过解释、承接与具体化实现，不通过把所有结论降成“可能有价值”实现。
- 面向降低 AIGC 检测率（如朱雀等检测器）改写时，严禁为了“换词润色”反而引入 `X rather than Y` 对仗、冒号阶段式展开、倒装存在句、LLM 隐喻动词（如 `carving out`、`sidesteps`、`squeezes`）或句尾 `-ing` 结果尾巴；须打散模板骨架并改回“对象与条件 → 物理机制/限制 → 直接后果”的直白主谓宾句式，同时区分参考文献列表的格式误报。实操反模式、对比示例与检测报告排查流程见[降AI率实操与检测排查](references/detector-hardening.md)。

[示例与反例](references/examples.md)展示如何修改及何时不应改。

## 6. 审阅反馈与项目术语保护

若当前项目维护了独立的术语表、符号约定或锁定句式，仅在对应项目内按需遵守，不得把上一篇论文的术语习惯带入新稿。

面对审阅意见，先区分理解问题、修辞建议、事实核查和证据要求，再决定接受、局部接受或待核验。跨子领域读者反馈的规则化整理见[读者反馈](references/reader-feedback.md)。

## 7. 交付标准

成稿应让非完全对口的读者回答：本文在什么条件下解决什么问题，核心设计改了哪一部分，为什么有用，证据支持到哪里。

不存在必须减少的字数或 AI 词数量。交付前确认没有未经授权的事实、术语、数值、引文或定稿变更；无法完成的核对单独说明，不伪装成已经核验。

当交付物包含或生成 Word（`.docx`）文件时，建议遵守以下文档规范：
- **清除工具水印元数据**：禁止保留 `python-docx` 默认写入的 `comments = "generated by python-docx"` 及 `author = "python-docx"`；生成或保存 `.docx` 时应显式设置 `doc.core_properties.comments = ""`，并将 `author` 与 `last_modified_by` 设为用户指定署名或空字符串 `""`。
- **引用角标与超链接挂载**：正文中的数字文献引用（如 `[1]`、`[1,2]`、`[3–7]`）应去除前置空格，以 Word 原生上标（`<w:vertAlign w:val="superscript"/>`）挂载，并通过内部书签超链接（`<w:hyperlink w:anchor="ref_N">`）跳转至文末对应的参考文献条目；文末参考文献中的 `https://doi.org/...` 应绑定为可点击的外部网页超链接。
